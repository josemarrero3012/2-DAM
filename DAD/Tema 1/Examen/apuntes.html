La historia: el programa explicado sin informática

🗣️ lenguaje humano

Antes de leer una sola línea de código, imagina una biblioteca de barrio de verdad. El programa del examen copia exactamente cómo funciona. Cada archivo es un personaje:

📇
La ficha
Libro.cs · Model

Una ficha de cartulina en blanco con 5 casillas: número, título, género, precio y "¿disponible?". No piensa ni hace nada: solo guarda datos.

📦
El almacén
LibroService.cs · Service

El sitio de donde salen las fichas. Aquí es un almacén de mentira: siempre entrega las mismas 4 fichas escritas a mano.

🧑‍💼
El bibliotecario
MainViewModel.cs · ViewModel

El cerebro. Tiene las fichas sobre la mesa, apunta lo que el cliente rellena y decide si se puede añadir un libro.

🪟
El mostrador
MainWindow.xaml · View

Lo que ve el cliente: el formulario, la tabla y el botón. No decide nada: solo enseña y recoge.

Y las piezas que los conectan

  • 🧵 Binding = un hilo invisible que cose cada casilla del mostrador con una libreta del bibliotecario. Lo que escribes en la casilla aparece en la libreta, y al revés.
  • 🔔 Command = el timbre del mostrador. El botón no hace el trabajo: solo toca el timbre y el bibliotecario actúa.
  • 🚦 CanExecute = el bibliotecario tapa el timbre (botón gris) si la ficha no tiene título.
  • 📢 INotifyPropertyChanged = un altavoz: cuando el bibliotecario cambia algo, grita "¡ha cambiado X!" y el mostrador se actualiza.
  • 🛎️ ObservableCollection = un tablón con campanita: cada vez que se cuelga o se quita una ficha suena, y la tabla se redibuja.
  • 🪪 DataContext = el cartel del mostrador que dice "le atiende: este bibliotecario". Así cada hilo sabe a quién ir.
  • 🤝 Inyección = cuando contratas al bibliotecario le das tú el almacén; él no se construye uno propio.

La historia completa en 6 frases

  1. Se abre la biblioteca: alguien crea el almacén y contrata al bibliotecario dándoselo.
  2. El bibliotecario pide las fichas al almacén y las cuelga en el tablón: la tabla se llena con 4 libros.
  3. El cliente escribe un título: el hilo invisible lo lleva letra a letra a la libreta del bibliotecario.
  4. Como ya hay título, el bibliotecario destapa el timbre: el botón se pone azul.
  5. El cliente pulsa el botón: el bibliotecario rellena una ficha nueva y la cuelga; la campanita suena y aparece una fila más.
  6. El bibliotecario borra el título de su libreta: la casilla se vacía y el timbre vuelve a taparse.

¿Por qué separarlo así?

Si mañana el mostrador cambia de diseño, el bibliotecario sigue igual. Si cambias el almacén falso por una base de datos real, ni el mostrador ni el bibliotecario se enteran. Cada uno hace una sola cosa. Eso es MVVM.

Cómo se lee un {Binding}: anatomía

{Binding NuevoTitulo, UpdateSourceTrigger=PropertyChanged}
"Coso esto con un hilo…"
"…a la libreta llamada NuevoTitulo del bibliotecario"
"…y le paso el dato con cada tecla (no cuando salga de la casilla)"

Se lee de izquierda a derecha como una frase: "Enlaza [esta propiedad del control] con [la propiedad NuevoTitulo del DataContext], actualizando [cada vez que cambie]".

Definición para el examen

MVVM (Model-View-ViewModel) es un patrón de arquitectura que separa la interfaz de la lógica. La Vista se conecta al ViewModel mediante Data Binding y Comandos, de forma que el code-behind queda prácticamente vacío. Ventajas: testeable, mantenible, diseñador y programador trabajan por separado.

¿Qué es un "mockup" / servicio simulado?

Un servicio que devuelve datos falsos en memoria (lista escrita a mano) en vez de leer de una base de datos. Sirve para desarrollar y probar la interfaz antes de tener la BD. Gracias a la interfaz, cambiarlo por el real es trivial. Es lo mismo que ServicioMensajesSimulado : IServicioMensajes del ejemplo 4_Inyección.

04

ViewModel · línea a línea

los ⟦n⟧ del código
  • 1partial + ObservableObject. El Toolkit usa un Source Generator que escribe la otra "mitad" de la clase en tiempo de compilación. Sin partial → error: no puede añadir código. ObservableObject ya implementa INotifyPropertyChanged.
  • 2readonly: solo se asigna en el constructor. Tipo = la interfaz, no la clase.
  • 3ObservableCollection avisa a la vista cuando se añade o borra un elemento (INotifyCollectionChanged). Con List la ListView no se refrescaría al hacer Add.
  • 4Libro? = puede ser null (al arrancar no hay nada seleccionado). Enlazado a SelectedItem de la ListView.
  • 5NotifyCanExecuteChangedFor: cada vez que cambia el título, le dice al comando "vuelve a mirar si puedes ejecutarte" → el botón se activa/desactiva solo.
  • 6Opciones del ComboBox (ItemsSource). Es List porque no cambia nunca.
  • 7Inyección de dependencias por constructor: el ViewModel recibe el servicio, no hace new LibroService(). Consecuencia: ya no tiene constructor vacío → no se puede crear desde XAML.
  • 8Convierte la List del servicio en ObservableCollection. Se asigna a Libros (propiedad, mayúscula), no a _libros, para que se notifique.
  • 9Regla de negocio con expression-bodied (=>). IsNullOrWhiteSpace también rechaza " " (solo espacios). Si es false → botón gris.
  • 10[RelayCommand] genera la propiedad AgregarLibroCommand (nombre del método + Command). CanExecute = nameof(...) le dice qué regla consultar.
  • 11Libros.Add dispara CollectionChanged → aparece la fila nueva sin hacer nada más.
  • 12Vaciar NuevoTitulo limpia el TextBox (TwoWay) y vuelve a deshabilitar el botón (por ⟦5⟧).

Regla del nombre generado

Tú escribesEl Toolkit genera
private string _nuevoTitulopublic string NuevoTitulo

Campo: "quita el guion, sube la primera". Método: "nombre + Command".
En XAML y en el código siempre se usa la versión pública.

"P.O.R. favor, compila"

Partial · ObservableObject · RelayCommand

Las 3 piezas del Toolkit que tienen que estar sí o sí. Y para propiedades: [ObservableProperty] sobre un campo privado con _minúscula.

Paquete NuGet: CommunityToolkit.Mvvm (en el .csproj, versión 8.2.2).

Detalle fino que cae en examen

ObservableCollection notifica añadir / quitar / mover elementos, pero NO notifica si cambias una propiedad dentro de un Libro existente (ej. Libros[0].Titulo = "X"), porque Libro es POCO y no implementa INotifyPropertyChanged.
Id = Libros.Count + 1 funciona aquí porque nunca se borra; si se borrasen libros podrían repetirse Ids.

El ViewModel resumido para cualquiera

"El bibliotecario guarda la lista de libros, lo que el cliente está escribiendo y el libro elegido. Al empezar pide los libros al almacén. Solo deja pulsar el botón si hay título, y al pulsarlo crea un libro con lo escrito, lo añade a la lista y limpia el título."

Lo que NUNCA hace el bibliotecario

No toca la pantalla: no escribe txtTitulo.Text, no pinta filas, no colorea el botón. Solo cambia sus libretas, y los hilos y el altavoz se encargan del resto. Por eso se puede probar sin pantalla.

05

View · MainWindow.xaml

<Window x:Class="BibliotecaIntegral.MainWindow">
  • 1Language="es-ES": cultura española en los bindings → {0:C} sale en € y con coma decimal. Sin él, WPF usa en-US ($).
  • 2UpdateSourceTrigger=PropertyChanged: actualiza el ViewModel con cada tecla. Por defecto, TextBox.Text lo hace en LostFocus (al salir de la caja). Sin esto el botón no se activaría al escribir.
  • 3ItemsSource = la lista de opciones. SelectedItem = la opción elegida (TwoWay).
  • 4CheckBox → IsChecked ⇄ bool.
  • 5Command en lugar de Click: cero código en el code-behind. El botón se deshabilita solo si CanExecute = false.
  • 6ItemsSource enlazado a la ObservableCollection.
  • 7SelectedItem ⇄ LibroSeleccionado: al hacer clic en una fila el ViewModel lo sabe.
  • 8Dentro de cada fila el contexto ya es un Libro, por eso {Binding Id} y no {Binding Libros.Id}.
  • 9StringFormat={}{0:C}: formato moneda (C = Currency). El {} "escapa" las llaves para que XAML no lo confunda con otra extensión de marcado.
  • 10Ruta con punto (LibroSeleccionado.Titulo). Si es null el binding falla y muestra FallbackValue = "Ninguno".

Modos de Binding

OneWay: VM → Vista (TextBlock). TwoWay: VM ⇄ Vista (TextBox.Text, SelectedItem, IsChecked lo son por defecto). OneTime: solo al cargar. OneWayToSource: Vista → VM.

La pregunta estrella del examen

¿Por qué el DataContext se asigna en el code-behind y no en el XAML? → Porque MainViewModel recibe ILibroService por el constructor. XAML solo sabe instanciar objetos con constructor vacío. Esto no rompe MVVM: el code-behind solo "cablea", no tiene lógica.
🗣️ En humano: el XAML solo sabe contratar a gente que no pide nada para empezar. Nuestro bibliotecario exige que le den un almacén, así que hay que contratarlo "a mano" en el código.

Extra: d:DataContext="{d:DesignInstance Type=vm:MainViewModel}" (ejemplos 4) solo sirve para el diseñador de Visual Studio (IntelliSense en bindings); se ignora al ejecutar.

Lo que el Toolkit escribe por ti

Source Generator

Esto es lo que había que escribir a mano en MVVM tradicional (ejemplos 01–03). Si te preguntan "¿qué hace [ObservableProperty]?", la respuesta es este código. 🗣️ En humano: las pegatinas son como un ayudante que escribe por ti las 20 líneas aburridas que siempre son iguales.

El setter tradicional, leído en voz alta

"Cuando alguien quiera cambiar el título: si el nuevo valor es distinto del que tengo, lo guardo, grito por el altavoz que el título cambió y le digo al botón que vuelva a comprobar si puede encenderse."

El altavoz 📢

INotifyPropertyChanged = la clase grita "¡ha cambiado la propiedad X!" y la Vista, que escucha el evento PropertyChanged, se actualiza.
[CallerMemberName] rellena solo el nombre de la propiedad que llama → no hay que escribir "NuevoTitulo" a mano.

RelayCommand = el puente

Implementa ICommand: Execute (qué hacer), CanExecute (¿se puede?), evento CanExecuteChanged (avisa para volver a preguntar). En el tradicional se programa a mano (RelayCommand.cs, guarda un Action); con Toolkit viene hecho.

Atributos del Toolkit: tabla rápida

Atributo / claseSe pone sobre…Qué hace🗣️ En humano
ObservableObjectla clase (herencia)Base que implementa INotifyPropertyChanged y da SetProperty().Trae el altavoz de fábrica.
[ObservableProperty]campo privado _xGenera la propiedad pública X con notificación de cambio."Haz pública esta libreta y que avise al cambiar."
[NotifyCanExecuteChangedFor(nameof(C))]campo observableAl cambiar el campo, reevalúa el CanExecute del comando C."Si cambio, que el botón C se lo replantee."

La evolución contada como una historia

¿Por qué la 02 "NO es MVVM"?

Porque la Vista tiene un manejador de evento en el code-behind que llama al ViewModel. La Vista "conoce" el tipo del ViewModel y hay lógica fuera de él. Funciona, pero acopla. La solución es ICommand (versión 03).

Inyección de dependencias en una frase

"Una clase no crea lo que necesita: se lo dan desde fuera (por el constructor)". El ViewModel depende de una abstracción (ILibroService) → podemos pasarle el simulado o el real. Ventaja: tests y cambio de implementación sin tocar el ViewModel.

"¿Qué pasa si…?" · preguntas tipo examen

try { } catch
Q1…quito partial de MainViewModel?
No compila. El generador necesita añadir la otra parte de la clase (propiedades y comandos). Además NuevoTitulo y AgregarLibroCommand no existirían.
🗣️ El ayudante no tiene dónde escribir su mitad.
Q2…uso List<Libro> en vez de ObservableCollection?
Carga los 4 iniciales, pero al pulsar Añadir la ListView no muestra el nuevo libro (List no lanza CollectionChanged), aunque sí está en memoria.
🗣️ Tablón sin campanita: la ficha se cuelga, pero nadie se entera.
Q3…quito UpdateSourceTrigger=PropertyChanged del título?
El valor solo llega al VM al perder el foco. El botón sigue gris mientras escribes y se activa al salir del TextBox.
🗣️ El hilo solo tira cuando sueltas la casilla.
Q4…quito [NotifyCanExecuteChangedFor]?
El comando nunca se entera de que el título cambió → el botón se queda siempre deshabilitado.
🗣️ Nadie le dice al bibliotecario que vuelva a mirar el timbre.
Q5…escribo "abc" en el Precio?
La conversión string→decimal falla: borde rojo (error de validación) y NuevoPrecio conserva su valor anterior. No hay excepción ni se cuelga.
Q6…escribo PrecioAlquiler = 2.50 sin la m?
Error de compilación CS0664: un literal double no se convierte implícitamente a decimal.
Q7…pongo el ViewModel en <Window.DataContext>?
Error: no tiene constructor sin parámetros. Por eso se hace en el code-behind con new MainViewModel(libroService).
Q8…en XAML escribo {Binding _nuevoTitulo}?
No funciona (no da excepción, solo un error de binding en la ventana de Salida). Binding solo ve propiedades públicas: hay que usar NuevoTitulo.
🗣️ Es la libreta privada: el hilo no llega.
Q9…en CargarDatos asigno _libros = … en vez de Libros = …?
Se salta el setter generado → no se notifica. Si la vista ya estaba enlazada seguiría mostrando la colección vieja. (El Toolkit avisa con un warning.)
Q10…no hay libro seleccionado?
LibroSeleccionado es null → LibroSeleccionado.Titulo no se resuelve → se muestra el FallbackValue "Ninguno".
Q11…dejo Libro como internal?
Accesibilidad incoherente: una interfaz/propiedad pública no puede exponer un tipo menos accesible.
Q12…escribo solo espacios en el título?
IsNullOrWhiteSpace(" ") = true → PuedeAgregar = false → botón gris. Con IsNullOrEmpty sí dejaría añadir.

Las 5 frases que tienes que poder escribir

  1. MVVM separa la interfaz (View) de la lógica (ViewModel) y los datos (Model), comunicados por Data Binding y Comandos.
  2. ObservableCollection notifica a la vista al añadir o eliminar elementos.
  3. [ObservableProperty] genera la propiedad pública con notificación de cambio; la clase debe ser partial.
  4. [RelayCommand] genera un ICommand; CanExecute habilita o deshabilita el botón automáticamente.
  5. Con inyección por constructor el ViewModel depende de una interfaz, por eso el DataContext se asigna en el code-behind.
